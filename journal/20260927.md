## Glossary

First, let me understand the terms written in the [Core](../docs/Core.pdf) document.

**nvidia-smi**: stands for **NVIDIA System Management Interface (SMI)**. Ships with NVIDIA display drivers. Underlying is NVML.
**NVML**: **NVIDIA Management Library**. Thread-safe C-based proprietary API for NVIDIA **system-level** monitoring and management; it monitors properties of the entire GPU like model, driver version, temperature, fan speed, VRAM usage, total VRAM allocation, clock speeds. It reports these by acting as PLI-wrapper to NVIDIA's propretary kernel-model drivers, querying on-chip registers, system files, VRAM memory. 

**Nsight**: proprietary tools for end-user application and kernel instrumentation. Does this by:
- API interception and tracing: **Nsight Systems (nsys)** and **CUPTI (CUDA Profiling Tool Interface)** dynamically hook into function calls, graphics and compute APIs. (**TODO: compare to linux perftools.)
- Explicit Annotation: NVIDIA Tools eXtension SDK (NVTX). C, C++, Py API to insert custom structures, named code ranges, resource categories in the application program. These show up in runtime profile of app on Nsight tools.
- Sampling and performance counters: automatically collected by NVIDIA hardware. These are sampled and profiled by Nsight tools.
- High-level decorators and context management: in Py function calls, transforms or adds context to the function call using light-weight function context manager and decorators. **TODO: read about lang features which allow _lightweight context management_ of its functions utilized here by NVIDIA Nsight tools.**

**nsys**: **Nsight Systems**. Its a complete end-user application (complete = CPU + GPU) profiler composed of _statistical sampler with tracing features_. 
see Overview [here](https://docs.nvidia.com/nsight-systems/InstallationGuide/index.html) for proof of assertions below.
- **Sampling**: _periodically_ stops the user kernel and switches to proprietary Nsight kernels to sample backtraces of active threads' call stacks (**TODO: what does 'call stacks' mean for 'active threads' in a GPU?**) and samples performance counters on chip. Sample size effects on variance applies. **TODO: sampling how? independent and identical? correlated in what way? how do we know for sure?**
- **Tracing**: exact and longitudinal data on the profilee's execution. **TODO: how are such exact _traces_ collected? Is the mechanism _massless_ now that it is definite and longitudinal execution sampling? What kind of objects can such exactly-traced profilee be?**

**ncu** : **Nsight Compute**. Compared to nsys which profiles the entire application9 _macroscopic_), this proprietary Nsight tool profiles single CUDA kernels at the fine-grained hardware level .
See [this page](https://docs.nvidia.com/nsight-compute/ComputeTriage/index.html) for proof of assertions below.
- nsys being the app-wide profiler has lower mass. ncu is far from low-mass profiler: it greatly slows down the profiled Kernel (**TODO: compare with Intel's Pintools.**)
- Looks like detailed API is present for precise hardware counter collector and custom reports. See [here](https://docs.nvidia.com/nsight-compute/CustomizationGuide/index.html#custom-descriptions).
- They even have programming constructs for "rules" (called [NvRules](https://docs.nvidia.com/nsight-compute/CustomizationGuide/index.html#nvrules-api) which are defined code to sift through the millions of performance metrics and parse them programmatically for display to the instrumentation engineer.

**HAZARD: it seems 590.104.02 fixed a [bug for GPU Page Table allocating $\geq 2$ GiB](https://www.linuxcompatible.org/story/nvidia-linux-driver-59510402-fixes-pagetable-and-wayland-hdr-crashes/) from earlier drivers.**
> NVIDIA's Linux kernel driver maps virtual addresses down to physical VRAM using hierarchical page tables, and those structures are sized using a signed 32-bit integer. 
> That type tops out at 2,147,483,647 bytes, a touch over 2 GiB. 
> Push past that boundary and the size overflows into a negative number. 
> The allocator then reads an impossible size and rejects the request. 
> Big workloads simply fail. 
> That sounds like an edge case until you weigh who actually hits it. 
> High-VRAM cards like the RTX PRO line and data-center accelerators map address spaces well past 2 GiB. 
> So do large multi-monitor setups and AI/HPC workloads pushing big tensors through virtual memory. 
> Before today any of those could trip the wall; after today, page tables over 2 GiB allocate correctly. 
> It's a textbook integer-width bug that hides in plain sight until a workload finally gets big enough to matter.
So I may need to upgrade my nvidia driver if GPU Page Table allocated a memory of stretch about $2$ GiB or more.

## VENV cheatsheet

I am used to `conda` but never used `venv` to  manage my Python3 virtual environment.
Nevertheless, this CUDA Kernel training phase is a good chance to learn `venv`. Here is a quickstart I have asked Google and written for my review.

1. Create a virtual environment named \<folder-name\> `python3 -m venv <folder-name>`

2. Activate the virtual environment using `source .venv/bin/activate`

3. Install your required Python packages. `pip install <package_name>`

4. Check if a specific package is installed in the active environment. `pip show <package_name>`

5. Alternatively, list all installed packages in the environment. `pip list`

6. Upgrade an existing package to the latest version. `pip install --upgrade <package_name>`

7. Uninstall and remove a package from the environment. `pip uninstall <package_name>`

8. Deactivate and exit the virtual environment. `deactivate`

### CUDA initialization failure — resolved (2026-09-27)

**System.** Pop!_OS 24.04, NVIDIA GeForce RTX 4070 Laptop GPU, driver branch 580.173.02.

**Symptom.** `cuInit` failed at context creation — PyTorch (`torch.cuda.is_available()` → False, "CUDA driver initialization failed") and a native C++ smoke test alike. Ruled out before diagnosis: graphics profile (system76-power switches), environment variables, Python layer (C++ binary failed identically), permissions (root failed identically), package corruption (metapackage reinstall changed nothing). `lsmod` showed all four modules loaded, including `nvidia_uvm` — so not a module-loading failure.

**Root cause.** The kernel module *flavor*. `dpkg -l` showed `nvidia-dkms-580-open` / `nvidia-driver-580-open` / `nvidia-kernel-source-580-open`. The `system76-driver-nvidia` metapackage lists `-open` first in its dependency alternatives, so APT selects it by default — and reinstalling the metapackage re-selects it, which is why that step was a no-op. Same configuration, same GPU, same failure documented in [pop-os/pop#3654](https://github.com/pop-os/pop/issues/3654); the ordering issue is [pop-os/pop#3640](https://github.com/pop-os/pop/issues/3640). The precise defect inside the open module was never root-caused upstream (marked: unresolved), but the flavor-dependence is established by direct experiment below.

**Fix.**
```bash
sudo apt install nvidia-driver-580   # names the proprietary flavor explicitly;
                                     # APT swaps out the three -open packages
sudo apt autoremove --purge
sudo reboot
```
Key point: install `nvidia-driver-580` *by name*, never the bare `system76-driver-nvidia` metapackage — the latter resolves back to `-open`.

**Verification.** C++ smoke test: `SUCCESS! Base system found 1 CUDA-capable GPU(s).` PyTorch: `True`, `NVIDIA GeForce RTX 4070 Laptop GPU`. Identical driver version both flavors → the flavor was the entire delta. Subsequently moved `system76-power graphics` to **hybrid**; both layers re-verified from the runtime-suspended state.

**Why the open flavor is fragile here (gloss).** The open modules aren't an open driver: userspace (CUDA, Vulkan, GL) stays proprietary, and the privileged kernel logic was relocated into firmware on the GSP, a RISC-V coprocessor on-die (which is why pre-Turing is unsupported — no GSP). NVIDIA's own README lists the costs of that relocation: slower GPU init, longer S3/RTD3 enter/exit latencies from restoring GSP state, RTD3 only on Ampere+. Those are precisely the laptop/hybrid-graphics code paths, and that's where the bug reports cluster (context creation, wake-from-D3, suspend). Deduction: desktop/datacenter parity is real (~1% per Phoronix); the laptop tail is not burned down. Imputation, well-supported: distros flipped defaults (NVIDIA at 560, Pop!_OS metapackage ordering) on the strength of parity measured on hardware unlike this one.

**Cost of running proprietary.** Open-only features per NVIDIA: Confidential Computing, GPUDirect Storage, HMM, fault-handler CPU affinity, DMABUF for CUDA allocations. Only HMM touches a kernel-development workflow (plain `malloc` pointers in kernels); `cudaMalloc`/`cudaMallocManaged` work identically, and explicit allocation is what hand-optimization pedagogy wants anyway. Everything that matters for kernel tuning — nvcc/PTX/SASS, Nsight Compute, CUPTI counters, `nvidia-smi` clock locking — lives above the kernel-module boundary and is flavor-invariant. Net cost for this machine's purpose: ~zero.

**Residuals.**
1. The metapackage ordering is unfixed upstream, and its alternatives now begin `nvidia-driver-595 | nvidia-driver-580-open | nvidia-driver-580 | …`. After any driver-branch upgrade, before treating a CUDA failure as new: `dpkg -l | grep -E 'nvidia-(driver|dkms|kernel)'` and check the flavor.
2. Hybrid mode leaves GPU clocks floating; for kernel benchmarks, lock clocks via `nvidia-smi` or discard warm-up runs.
3. Blackwell and later are open-flavor only — the proprietary escape hatch dies with this GPU generation. Non-actionable now; relevant at next hardware purchase.

**References.** [pop#3654](https://github.com/pop-os/pop/issues/3654) · [pop#3640](https://github.com/pop-os/pop/issues/3640) · [NVIDIA open-modules README](https://download.nvidia.com/XFree86/Linux-x86_64/580.119.02/README/kernel_open.html) · [NVIDIA R560 transition post](https://developer.nvidia.com/blog/nvidia-transitions-fully-towards-open-source-gpu-kernel-modules)
